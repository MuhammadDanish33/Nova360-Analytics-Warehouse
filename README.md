# NovaGroup Enterprise Database

**A multi-domain analytical data platform designed for cross-industry intelligence, fraud prevention, retail operations excellence, and renewable energy asset optimisation.**

---

## What is this?

NovaGroup is not a simple transactional database. It is a carefully engineered **enterprise analytical platform** that models three major business domains **Banking**, **Retail**, and **Energy** under one unified architecture.

At its heart sits a **shared Common schema**. This shared foundation allows the organisation to answer questions that span departments:

- How does a customer’s banking behaviour relate to their retail purchasing patterns?
- Can energy generation anomalies be correlated with customer vulnerability flags?
- How do high-risk banking customers behave as retail shoppers?

The design follows modern data-warehouse principles (star schemas, conformed dimensions, carefully enforced business rules) so that analysts, data scientists, and business stakeholders can trust the numbers they see.

## High-Level Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    Common Schema                            │
│  • Customer (single source of truth)                        │
│  • Date Dimension  • Time Dimension                         │
└──────────────────────────┬──────────────────────────────────┘
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Banking   │    │   Retail    │    │   Energy    │
│  (Fraud &   │    │ (Supply     │    │ (Generation │
│  Risk)      │    │  Chain)     │    │  & Market)  │
└─────────────┘    └─────────────┘    └─────────────┘
```

Everything is organised into four schemas:

| Schema   | Purpose                                      | Style                  |
|----------|----------------------------------------------|------------------------|
| Common   | Shared customer identity + calendar/time     | Conformed dimensions   |
| Banking  | Payments, fraud detection, investigations    | Heavy fact tables + risk features |
| Retail   | Sales, inventory, promotions, supply chain   | Classic retail star schemas |
| Energy   | Generation, curtailment, maintenance, markets| Time-series + asset hierarchy |

## 1. Common Domain — The Glue

### Customer
The single most important table in the entire system.

Every customer has one record that is shared across Banking, Retail and (indirectly) Energy. This enables true **360° customer understanding**.

Key attributes that reveal design intent:
- `RiskRating` (Low / Medium / High) with a hard constraint
- `VulnerabilityFlag` + `VulnerabilityType` — critical for regulatory and ethical analysis
- `CustomerExternalRef` — unique business key for integration with source systems
- Soft-delete pattern via `IsActive`

### DateDim & TimeDim
Proper calendar and time-of-day dimensions.  
These are the foundation for every time-based analysis (daily, hourly, seasonal, weekend effects, etc.).

## 2. Banking Domain — Fraud & Risk Intelligence

This is the most sophisticated part of the model. It is clearly designed for a modern payments / fraud operations team.

### Core Dimensions
- **DimAccount** — linked to Customer, with status lifecycle rules (`CloseDate >= OpenDate`)
- **DimBeneficiary** — who money is sent to
- **DimDevice** & **DimLocation** — critical for behavioural biometrics and geo-risk
- **DimAlertRule**, **DimInvestigator**, **DimCasePriority**, **DimFraudType**, **DimInterventionType**

### Fact Tables (the real analytical power)

| Fact Table              | What it answers                                      |
|-------------------------|------------------------------------------------------|
| FactTransaction         | Every payment with full context (device, location, CoP result, new beneficiary flag) |
| FactTransactionEvent    | Full event timeline of a transaction (Created → Authorised → Blocked → Released…) |
| FactDigitalSession      | Login behaviour, failed attempts, session risk score |
| FactFraudAlert          | Alerts generated by rules, with risk score and status |
| FactCase                | Investigation cases, SLA tracking, confirmed fraud flag, loss amount |
| FactIntervention        | Customer contact outcomes |
| FactReimbursement       | How much the bank paid back to victims |
| FactFundRecovery        | How much was recovered from receiving banks |
| FactRiskFeature         | Daily snapshot of velocity, new beneficiaries, device/location change flags, derived risk score |
| FactAccountNetwork      | Graph-ready relationships between accounts (Sender / Receiver / SharedDevice) |

**Design insight worth noting:**  
`FactRiskFeature` has a unique constraint on `(AccountID, FeatureDateKey)`. This is a deliberate daily feature store perfect for training machine-learning models without having to re-aggregate every time.

## 3. Retail Domain — Operations & Commercial Performance

Classic but complete retail data warehouse.

### Key Dimensions
- Products (with margin and perishability rules)
- Locations (Store / Warehouse / Fulfilment Centre)
- Suppliers + Product-Supplier bridge (many-to-many with primary supplier flag)
- Channels, Promotions, Return Reasons, Inventory Movement Types

### Fact Tables
- **FactSalesLine** — the commercial heart (quantity, discount, net sales, cost, gross profit)
- **FactInventorySnapshot** — daily on-hand / available / reserved / damaged
- **FactInventoryMovement** — full movement history
- **FactOnlineOrderLine** — fulfilment performance (ordered vs fulfilled vs cancelled vs substituted)
- **FactPurchaseOrderLine** + **FactGoodsReceipt** — procurement cycle
- **FactStockTransfer** — inter-location logistics
- **FactReturnLine** — returns with reason and resaleability
- **FactPromotionPerformance** — baseline vs actual vs incremental lift
- **FactForecast** — demand planning

Business rules are enforced at the database level (e.g. `UnitPrice >= UnitCost`, `AvailableQty <= OnHandQty`, quantity consistency on orders).

## 4. Energy Domain — Asset & Market Performance

Built for a renewable energy operator (Wind / Solar / Battery).

### Hierarchy
- Regions → Assets (with parent-child capability) → Components
- Weather stations linked to regions
- Markets, Services, Counterparties

### Fact Tables
- **FactEnergyInterval** — the highest-granularity fact (generation, forecast, curtailment, battery charge/discharge, SOC, availability, carbon intensity)
- **FactCurtailmentEvent** — why and how much energy was lost
- **FactDispatchInstruction** — market instructions vs actual delivery
- **FactWeatherObservation** — wind speed, irradiance, temperature
- **FactAssetAvailability** — daily availability percentage
- **FactMaintenanceWorkOrder** & **FactAssetFault** — reliability and cost of downtime
- **FactCommercialSettlement** — revenue, cost, net profit
- **FactGenerationAnomaly** — expected vs actual with revenue and carbon impact

Notice the strong emphasis on **time-series integrity** and **physical constraints** (State of Charge 0–100 %, Availability 0–100 %, no negative generation, etc.).

## What Analyses Become Possible?

Because of the shared Customer and Date/Time dimensions, the platform supports both **domain-specific** and **cross-domain** questions.

### Banking / Fraud
- Real-time style risk scoring using velocity features
- False positive rate of alert rules
- Investigator productivity and SLA breach analysis
- Recovery rate vs reimbursement rate
- Network analysis of mule accounts (via FactAccountNetwork)
- Device & location change patterns preceding fraud

### Retail
- Gross margin by product / channel / location
- Promotion lift analysis
- Inventory health (days of cover, damaged stock, stockouts)
- Online fulfilment performance (substitution & cancellation rates)
- Supplier reliability vs lead time

### Energy
- Forecast accuracy vs actual generation
- Curtailment root-cause analysis
- Battery cycling and degradation cost
- Availability vs weather correlation
- Commercial performance by market and counterparty

### Cross-Domain (the real differentiator)
- Do high-risk banking customers also show unusual retail return patterns?
- Is there a relationship between customer vulnerability flags and energy consumption / payment behaviour?
- Can retail promotion periods be correlated with spikes in banking transaction velocity?
- Customer lifetime value that includes both banking and retail contribution

## Design Quality Signals (What a Hiring Manager Should Notice)

1. **Business rules live in the database**  
   Almost every important constraint is declared with `CHECK` constraints rather than left to application code. This is mature engineering.

2. **Proper dimensional modelling**  
   Surrogate keys, conformed dimensions, clear fact tables, bridge tables where needed.

3. **Lifecycle thinking**  
   Account open/close dates, case open/close timestamps, asset commission/decommission, promotion start/end — all enforced.

4. **Feature store readiness**  
   `FactRiskFeature` is already structured as a daily feature snapshot with uniqueness enforced.

5. **Graph readiness**  
   `FactAccountNetwork` is designed for network/fraud-ring analysis.

6. **Regulatory awareness**  
   Vulnerability flags, CoP (Confirmation of Payee) results, reimbursement tracking — these are not accidental; they reflect real UK banking regulation (APP fraud, Vulnerable Customer requirements, etc.).

7. **Physical & financial integrity**  
   Energy tables respect physics (SOC, availability). Retail tables respect commercial reality (price ≥ cost). Banking tables respect money movement rules.

## How to Use This Repository

1. Run the full SQL script against a SQL Server instance to create the `NovaGroup` database.
2. Populate the dimension tables first (especially `Common.DateDim`, `Common.TimeDim`, and `Common.Customer`).
3. Load fact tables respecting foreign-key order.
4. Start with the analyses listed above — many can be answered with relatively simple SQL once the data is loaded.
